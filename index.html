AI case-intake assistant for a homeopathy practice

Status Building, running evals before rollout
Client A homeopathy practitioner, expanding to her wider practice
Role Sole builder — pipeline, evals, guardrails
Stack RAG pipeline: chunking, embeddings, retrieval, LLM generation
Handles Patient case sheets — health data, access-scoped

The problem

A homeopathy practitioner works from years of case notes and reference material — materia medica, repertories — as unstructured documents. Every new patient case means manually cross-referencing symptoms against that material from memory and page-flipping, which is slow and depends entirely on what she can recall in the moment.

What I'm building

A retrieval-augmented pipeline that takes a case sheet (text, PDF, Word, or a photo of handwritten notes), retrieves the matching rubrics and remedy references from her own knowledge base, and returns a structured draft: case summary, mind and physical rubrics, a remedy suggestion, and a repertory chart — for her to review and confirm, not to act on unread.

Safety and privacy, by design

Two things shaped the architecture before a line of pipeline code went in. First, this touches medical judgment, so every output has to trace back to a specific rubric or remedy reference in her material rather than the model generating freely — and when retrieval doesn't find a solid match, that gets flagged instead of quietly producing a confident-sounding answer anyway. Second, case sheets are patient health data, so access is scoped to the practitioner and nothing is retained beyond what a session needs — that boundary has to hold before this ever reaches a second doctor's patients.

Where I changed course

My first pass let the model generate the remedy suggestion directly from the case description. Once real case sheets went through it, that was clearly the wrong shape for a health-adjacent output — confident-sounding suggestions with no visible link back to a source. I re-scoped it around retrieval-grounded generation, and I'm now building the evals — testing relevance and groundedness against real cases — before deciding it's accurate enough to put in front of a second doctor's patients.

School management app for Novelle Cambridge Global School

Status Live since Aug 2026
Users ~100 parents, 15 staff
Role Product, architecture, build, support
Stack Expo / React Native, Supabase (Postgres, RLS, Storage), Vercel, Web Push
Links Live app  /  GitHub

The problem

A school running attendance, parent communication and notices on paper and WhatsApp groups. Parents missed updates, teachers had no single place to record the day, and the leadership had no overview.

What I built

A progressive web app that installs on any phone without an app store. Parents log in with their child's admission number and see attendance, class diary, announcements, the school calendar and photos, and can chat directly with staff. Staff get role-based screens: teachers scoped to their own classes, the Principal and Headmistress with school-wide dashboards and leave-request approvals. Push notifications built from scratch on Web Push. Multi-tenant from the first migration, with row-level security enforcing data boundaries in the database rather than the UI.

Outcome

Shipped to parents at a parent-teacher meet with printed credentials. One month in, no major issues reported and the school has asked for more features, including letting the Principal and class teachers start chats with any parent. Now being forked into a whitelabel platform for other schools.

Three roles, one codebase, different worlds

The same home screen adapts to who's logged in. This isn't three separate apps stitched together — it's one set of components with row-level security in the database deciding what each session can even query, so the boundary isn't just a hidden button in the UI, it holds even if someone inspects the network traffic.

Parent / student
Sees their own child's world: attendance, class diary, notices, and a direct line to raise a concern. No visibility into other classes or staff-only tools.
Teacher
Adds "My Classes," "Class Diary," and "Message a Parent" — scoped to the classes they actually teach. RLS enforces this at the database level, not just by hiding the button.
Principal / admin
Full school-wide reach: manage staff and classes, approve leave requests, see attendance across every class at once. The only role that can see across class boundaries.
Swipe to see the teacher and principal views.

What went wrong, and how I found it

After go-live I found that two security policies were missing a class-level check, so any parent could technically see another class's notices and photos. The cause was an "if role is unknown, allow" branch. I fixed it, then audited every class-scoped table directly against the live database policies rather than trusting migration success messages. Separately, the free database plan hit 135% of its bandwidth quota; I traced it through the query logs to full-resolution photos being re-downloaded on every visit, added device-side caching and upload compression, and usage dropped to 38% over the next billing cycle.

Rail bearing fault detection for a railway R&D contractor

Status In build, paid engagement
Client 2-person team contracted to test 15,000 wheels
Role Scoping, quoting, modelling, dashboard
Delivery Milestone-based freelance engagement
Infra AWS EC2, set up and run by me

The problem

The client tests rail wheel bearings with two instruments: a static test device and a handheld dynamic tester. They need each wheel diagnosed in under a minute so they can process around 400 wheels a day, and the diagnosis has to be visible on a dashboard rather than buried in instrument output.

What I'm building

Two parts. A rule-based system for the dynamic tests, using the client's own fault-detection rules, and a machine-learning model for the static tests trained on their labelled data. Scope was narrowed in two client calls: licensing and hardware integration were pushed to later phases so the first milestone could be a data-validation step, before any price was locked.

Why it matters to me

This is the project where my mechanical engineering background and my AI product work meet. Understanding what a bearing failure physically looks like is what made the scoping conversations credible.

Clearwayy, a QR-based vehicle notification service

Status Live
Role Idea to launch, solo
Stack Emergent, Vercel, WhatsApp, Google Sheets, Make.com
Link clearwayy.in

The problem

Your car is blocking someone and they have no way to reach you without your phone number on the windscreen. In an emergency, nobody knows who to call.

What I built

A QR sticker for the vehicle. Scanning it lets a stranger notify the owner over WhatsApp, or alert a family member in an emergency, without ever revealing the owner's identity or number. Built as a no-code workflow first to prove the idea cheaply before writing any software.

What it shows

Knowing when not to write code. The whole thing runs on automations and a spreadsheet, which was the right size for the problem.

The flow, end to end

Six screens, no app install required for either side. The person scanning the QR code never sees the owner's phone number — the owner's identity stays behind the automation the whole way through.

How I build with AI

I don't write most of the code by hand. I run a loop where I stay in charge of the decisions and let the tools do the typing.

Diagnose first

I describe the symptom to Claude, ask it to draft a precise investigation, and read the findings before approving any change. No fix without a root cause.

Build in small, reviewed steps

Claude Code makes the change. I review the diff, then commit. Big features are split into additive steps so a bad one can be reverted alone.

Verify in production

A green "deployed" badge isn't proof. I check the live bundle and the live database policies, because both have looked fine while being wrong.

AI decisions I've made, and why

Tools are easy to list. These are the calls that actually shaped a system.

Route on meaning, but never on a guess

For a healthcare platform, I led the team that replaced keyword-based triage with semantic routing: patient queries are embedded, matched against a specialty corpus in a vector database, and sent to the best-fitting available doctor. The important decision wasn't the embedding model. It was the confidence gate: a low-similarity match goes to a general practitioner, not to the "closest" specialist, and every decision is written to an audit table with its score and fallback reason. Thresholds live in configuration, not code, so clinicians can tighten them for high-risk specialties without a deploy.

Mask before you retrieve

On a conversational AI for a large US healthcare organisation, historical conversations were the retrieval source. We designed PII masking into the ingestion pipeline from day one rather than filtering model output afterwards, so patient identifiers never entered the index in the first place. Fixing this later would have meant rebuilding the corpus.

Delete the model nobody asked for

A video-analysis pipeline was running YOLO on GPU instances for multi-person bounding boxes and object-level detection, then a second model for lighting, then a third for the actual analysis. When I walked the client back through the requirement, they had never asked for bounding boxes or object detection; they wanted the analysis. We cut the detection stage, moved the analysis to Gemini, and got better results at a fraction of the compute cost. The expensive part of the system was there because it was technically interesting, not because anyone needed it.

Rules where the physics is known, ML where it isn't

For rail bearing diagnosis, the client already had fault-detection rules for their handheld dynamic tests, so that path stays rule-based and explainable. The static-test data has labelled defect spectra and no established rules, so that path gets a trained model. Two instruments, two methods, one dashboard. Choosing ML for both would have looked more impressive and worked worse.
